# 241 · 多 gh 账号下的推送最佳实践（43 个仓库通用）

> **日期**: 2026-10-01
> **背景**: 本机登录了多个 GitHub 账号，活跃账号一度指向无权限的
> `<另一个账号>`，导致 `qwdingyu` 名下仓库推送全部报 `Repository not found`。
> **已确认 `qwdingyu` 名下有 43 个本地仓库**，本方案按"舰队级"设计。
> **工具**: [`deploy/scripts/git-push-preflight.sh`](https://github.com/qwdingyu/deploy/blob/main/scripts/git-push-preflight.sh)

## 一、先讲清机制（**不要凭直觉改这条**）

### 1.1 实测结论

```bash
# gh 凭据助手对 username 的反应（活动账号 = qwdingyu）
printf 'get\nprotocol=https\nhost=github.com\nusername=qwdingyu\n\n' \
  | gh auth git-credential get      → qwdingyu
printf 'get\nprotocol=https\nhost=github.com\nusername=<另一个账号>\n\n' \
  | gh auth git-credential get      → (空)

# 切换活动账号后，同样的请求
# 活动 = <另一个账号> 时，以上两条分别返回 <另一个账号> 与 (空)
```

**`gh auth git-credential` 完全忽略 `username=`，永远服务"活动账号"**，
且该命令**没有任何选账号的参数**。

### 1.2 由此得出的两个不可行方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 在 remote URL 里写 `https://qwdingyu@github.com/...` | ❌ 无效 | 凭据助手忽略 username |
| `url.<base>.insteadOf` 按仓库自动绑定账号 | ❌ 无效 | 同上，最终仍取活动账号 |

> **所以"每个仓库绑定自己的账号"这条路是走不通的。**
> 活动账号是**唯一**开关，跨组织时它必然是全局的、会被来回切换的。
> 唯一可靠的防线：**推送前核验 + 自动纠正**。

### 1.3 `Repository not found` 的真实歧义

这个报错**同时**意味着：仓库不存在 / 仓库存在但无权限 / 活动账号不是 OWNER / 网络异常。

更糟的是：**GitHub 对你无权查看的私有仓返回 404 而不是 403**（刻意设计，不泄露私有仓是否存在）：

```bash
GH_TOKEN=$(gh auth token --user <另一个账号>) gh api repos/qwdingyu/ZL.PlcSimulator
  → {"message":"Not Found"}                      # 无权限的私有仓
gh api repos/qwdingyu/definitely-not-exist-xyz
  → gh: Not Found (HTTP 404)                     # 真的不存在
```

**两者无法区分。** 所以脚本**不谎称**能区分，只回答"能不能推"，
并在失败时把两种可能一并列出。

## 二、最佳实践

### 2.1 铁律：推送前先跑核验

```bash
cd <任一仓库>
/path/to/git-push-preflight.sh          # 核验并自动纠正
git push
```

跨组织批量操作前，**先跑一次确定活动账号**：

```bash
gh auth status | grep -E "account|Active"
```

### 2.2 脚本做什么

| 步骤 | 行为 |
|---|---|
| 1 | 从 remote 解析出 `OWNER/REPO`（兼容 https / ssh / 已是 OWNER/REPO） |
| 2 | 探测活动账号对该仓的 `permissions.push` |
| 3 | 通过 → 退出 0 |
| 4 | 不通过 → 遍历本机已登录账号，**用各自 token 独立探测** |
| 5 | 找到有权账号 → `gh auth switch` → **复验** → 退出 0 |
| 6 | 全都不行 → 退出 1，并给出三条可执行的排查命令 |

### 2.3 三条设计原则

1. **不假定操作成功**：切换后**必须复验**，不复用切换前的结论。
2. **不制造不存在的修复**：本机 `credential.https://github.com.helper` 早已是
   `gh auth git-credential`（优先级高于全局 osxkeychain），**不需要**再执行
   `gh auth setup-git`。当时的误判是"osxkeychain 缓存凭据"，纠正它是**查配置**，
   不是加设置。
3. **不谎称能力**：无法区分 404 的两种成因，就不假装能区分。

### 2.4 43 仓库批量核验

```bash
# 盘点：哪些仓在当前活动账号下推不动
for d in /path/to/*/; do
  [ -d "$d/.git" ] || continue
  u=$(git -C "$d" remote get-url origin 2>/dev/null)
  case "$u" in *github.com/*)
    r=$(basename "$d")
    /path/to/git-push-preflight.sh --repo "$(echo "$u" | sed -E 's#.*github.com/##; s#\.git$##')" >/dev/null 2>&1 \
      || echo "推不动: $r" ;;
  esac
done
```

## 三、测试与变异验证

配套测试：`deploy/scripts/git-push-preflight.test.sh`（11 项）。

### 3.1 脚本自身有 4 个真实缺陷，**全部只有实跑才暴露**

| # | 缺陷 | 暴露方式 |
|---|---|---|
| ① | `probe_as` 传了账号参数却没用——`gh api` 永远用活动账号，探测形同虚设 | 用例 3 报"均无权限"但账号明明有权 |
| ② | `$VAR` 紧跟全角字符 → bash 把全角吞进变量名 → `set -u` 报 unbound | 用例 3 退出码 2 |
| ③ | `for + shift` 遍历 `"$@"` 破坏遍历；改下标后只增 `i` 却仍引用 `${1}` | `原始值：--repo` |
| ④ | `--repo` 传入的 `OWNER/REPO` 被 URL 归一化剥掉 owner | 退出码 2 |

> **②是同一个坑的第三次出现**：本会话在 CI 里已犯过一次
> （`$SIM_VERSION（`，见 `21843af`）。已系统性扫描全仓并统一加 `${VAR}`。

### 3.2 测试套件自身也有 2 个漏洞，被变异测试抓出来

| # | 漏洞 | 后果 |
|---|---|---|
| ① | 静态检查用 `grep -P`——**macOS 的 BSD grep 不支持 `-P`**，直接以退出码 2 失败 | 失败在 `if` 里等于"没发现问题" = **假绿** |
| ② | 断言只查"复验通过"这段**文字** | 删掉真正的复验动作、保留文字，仍能通过 |

> **漏洞①是本会话第三次"空输出 = 通过"**（前两次：变异测试、CI 日志判读）。
> **凡是"用某个命令的失败表达检查通过"的写法，都要警惕。**

修复①后改用 `python3` 精确检查；修复②见下方"近似等价变异"。

### 3.3 变异测试结果

| 变异 | 结果 |
|---|---|
| `probe_as` 退回用活动账号 | **2 失败** ✅ |
| 重新引入 `$VAR`+全角 | **1 失败** ✅ |
| `--repo` 取不到值 | **3 失败** ✅ |
| `probe_as` 恒返回成功 | **3 失败** ✅ |
| **跳过复验直接放行** | ⚠️ **未抓住——近似等价变异** |

**关于最后一条，如实说明**：`probe_as` 使用**显式 token** 探测，
复验检查的是"这个 token 能否推送"，而非"切换是否生效"。
我曾试图用 PATH 桩件模拟"切换声称成功但未生效"，
但桩件会同时破坏**账号发现**，脚本从"均无权限"分支退出——
**那个 exit 1 与复验无关，是个误导性测试，已删除**。

结论：这是一个**近似等价变异**，它移除的防御检查失败概率极低
（token 在发现与复验之间被撤销）。**不为迎合测试而写无意义的断言**，
如实记录比硬凑一个假通过更有价值。

## 七、试过但**行不通**的方案（勿重试）

### 7.1 `pre-push` hook —— 拦不住，且已移除

**设想**：用 `git config --global core.hooksPath ~/.githooks` 对**所有仓库**强制，
不依赖每个仓的 AGENTS.md（43 个仓只有 13 个有，且内容各异，必然漂移）。

**实测结论：拦不住。**

| 场景 | hook 是否执行 | 证据 |
|---|---|---|
| 正确账号 | ✅ 执行，核验通过，推送成功 | 探针行 `### HOOK 探针` 出现在输出中 |
| 错误账号 | ❌ **未执行** | 无探针行，只有 git 的 `remote: Repository not found.` |

**原因**：git 在运行 pre-push **之前**就已解析远端并解析凭据，
凭据失败时 git 直接退出，hook 根本没机会跑。
（测试时先确认了探针确实写入文件（grep 计数 = 1），否则"探针没打印"可能只是改动没落地。）

**已移除 hook 并注销 `core.hooksPath`。**
留着它只会在每次推送增加约 1 秒，并制造"已有防护"的错觉——
而它对主失败模式完全无效，这比没有防护更危险。

> **附带的第二个坑**：初版把远端 URL 从 **stdin** 读取。
> 实际上远端名/URL 在**命令行参数 `$1` `$2`**，stdin 里是待推的 ref 更新。
> 读错位置 → `remote_url` 为空 → `case` 落到 `*) exit 0` → **hook 静默变成空壳**，
> 而当时所有"测试"都返回 0，看起来一切正常。
>
> 另：第一个 `sed -n '1p'` 会把 stdin **整个读光**，第二个 `sed` 拿到空串。
> 要读多次必须先 `stdin_all="$(cat)"`。

### 7.2 因此，真正的防线只能是**推送前的显式动作**

```bash
./scripts/git-push-preflight.sh && git push
```

这是当前唯一被完整验证有效的手段。它在 git 接触远端**之前**就纠正了账号，
本次恢复作业中实测：活动账号为 `usethinklab` 时脚本自动切到 `qwdingyu`，推送随即成功。

## 八、本次事故：**我自己的测试脚手架差点删掉已推送的工作**

### 8.1 发生了什么

为端到端验证 hook，我反复用"空提交 + `git reset --hard HEAD~1`"清理现场。
**清理时无条件执行 `HEAD~1`**，当探针提交已被上一步 reset 掉时，
`HEAD~1` 就指向了**真实提交的父提交**——`abe205a`（§18 铁律）被吃掉，
随后 `git push --force-with-lease` 把它传播到了远程 main。

### 8.2 为什么丢了还能救回来

reflog 保留了完整链条，`abe205a` 对象仍在：

```
git reflog --date=iso
  abe205a HEAD@{...}: commit: docs(AGENTS): 新增 §18 多账号推送铁律…
  … 探针提交与 reset 交替 …
```

恢复：`git reset --hard abe205a && git push --force-with-lease origin HEAD`
（`--force-with-lease` 而非 `--force`，确保不会覆盖他人的新提交）。
最终本地与远程均为 `abe205a`，差异 0，全分支无残留探针。

### 8.3 教训

1. **清理测试现场前，先确认"要删的东西"确实还在**——
   判据用**提交信息**而不是位置：
   ```bash
   if [ "$(git log -1 --format=%s)" = "探针提交名" ]; then git reset --hard HEAD~1; fi
   ```
   事后我加了这道守卫，它确实拦下了一次误删。
2. **破坏性操作前先列出将被删除的提交**（`git log f996d46..HEAD`），
   逐个判断是探针还是真实工作，再动手。
3. **不要在真实仓库上做破坏性实验**。本次差点损失的是已推送到远程的工作。
